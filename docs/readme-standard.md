# README standard for a skills repo

A skills-repo README is not a library README. The reader arrives from skills.sh or a
search result and decides *"do I install this"* in about fifteen seconds, and the
install command is the conversion event. Everything below serves that.

`make check` enforces the mechanical half of this file. The rest is judgement and
lives with whoever writes the README — a validator can prove a section exists, never
that it is worth reading.

## Section order

```text
icon             — first content block, local asset
# Title
one-sentence value proposition: who it is for + what they get
badges           — three at most: CI, license, skills.sh
## Demo          — proof before prose; a GIF, cast, or a short real transcript
## Quick start   — the one install command, then the smallest real usage
## Skills        — the catalogue table; this is the product
## <workflow>    — only when the skills compose into a sequence
## Repository structure / agent notes
## Contributing · Support · License
```

Depth belongs in `docs/`, not inline. Ecosystem diagrams, repo trees and validation
internals sit below usage, never above it.

## Rules

**Icon.** Every repo opens with one, generated by the
[icon-designer-skills](https://github.com/Paldom/icon-designer-skills) pipeline:
`/icon-brief` → `/icon-draw` → `/icon-critique` → you pick → the master SVG lands in
`assets/icon.svg`. The critique step hands candidates back to a human on purpose;
that pick is not the agent's to make.

**Examples are skills-level, always.** Show what a *user* types: the install command,
a `/skill-name` invocation, or the plain-English ask the skill triggers on. Never show
a script that lives inside a skill — `python3 skills/foo/scripts/bar.py` is
implementation detail the reader must never need. If a skill's value can only be
demonstrated by running its internals, the SKILL.md is the thing to fix.

**Demo as code.** Commit the source and the render: a `.tape`
([terminaltor](https://github.com/Paldom/terminaltor)) for terminal work, a scenario
YAML ([screenshooter](https://github.com/Paldom/screenshooter)) for anything with a
browser, plus the resulting GIF. A one-off recording rots silently; a committed source
file regenerates and shows up in a diff when behaviour changes. Neither tool is a
dependency of the generated repo — they are authoring-time skills, and the artifact
they produce is what ships.

**Mark every step.** A flat numbered list claims everything is mandatory and ordered.
Each step in a procedure starts with exactly one bold marker:

```markdown
1. **[Required]** Install the skills — `npx skills add owner/repo`
2. **[Optional]** Record a demo GIF for the README
3. **[Afterward]** Once a skill exists, publish the repo with `/publish-repo`
```

`Required` · `Optional` · `Afterward`. Nothing else. Plain bold brackets survive every
renderer; `<details>`, GitHub alert syntax and emoji do not survive skills.sh.
Required is written out rather than implied by silence, so an unmarked step is a
detectable defect instead of an ambiguity.

**Attribution goes in the footer, not the badge row.** A repo scaffolded by
skillskit ends with:

```markdown
---

[![Built with skillskit](https://img.shields.io/badge/built%20with-skillskit-F5A623)](https://github.com/Paldom/skillskit)

Scaffolded with [skillskit](https://github.com/Paldom/skillskit) — eval-first Agent
Skills tooling. This line is yours to delete; nothing checks for it.
```

Three decisions worth stating, because each could have gone the other way:

- **It stays out of the three-badge row.** The cap exists because every badge above
  the fold competes with the repo's own value proposition. Relaxing it for the
  scaffolder's own badge would be exactly the self-dealing the cap guards against.
- **The claim is provenance, nothing more.** "Built with" is true at creation and
  makes no ongoing promise. A static image asserting *validated*, *eval-first* or an
  accuracy number would be a lie the moment someone stops running the gate — or
  copies the badge into a repo that never had one. The repo's own CI badge already
  carries the live signal, and it goes red when the gate does.
- **The gate never checks for it.** `create-skill-repo` writes the footer by default
  and `--no-attribution` omits it; the validator says nothing either way. A warning
  would be a requirement with plausible deniability, and requiring attribution in
  someone else's MIT-licensed repo is not a quality invariant — it is advertising.

Badge hosting is shields.io on purpose: GitHub proxies README images through camo, so
self-hosting the SVG would buy no traffic visibility while making one repo's default
branch a single point of failure for every repo that was ever generated.

**Deslop last.** Run `/deslop` over the README prose once every command, example and
claim is verified — voice only. It must not touch code fences, inline code, commands,
flags, paths, URLs, versions, numbers, headings, table cells, or step markers, and it
must not soften a claim, a negation, or a limitation. Re-run `make check` afterwards;
a desynced skills table is the failure mode to watch for.

## What `make check` verifies

| Rule | Severity |
| --- | --- |
| Icon image is the first content block and the file exists | error |
| `npx skills add <owner>/<repo>` appears | error |
| No skill-internal script path in any code fence | error |
| Every skill under `skills/` has a catalogue row linking its folder | error |
| Every catalogue link points at a skill that exists | error |
| Referenced local images exist | error |
| Step markers use the three allowed words | error |
| A procedure mixes marked and unmarked steps | warning |
| No demo media referenced anywhere | warning |

Shape only. A README can satisfy every line above and still be bad.
